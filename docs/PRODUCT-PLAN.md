# 공모아: 기능 기획과 UX 설계

검토일: 2026-10-25 (한국 시간). 대상: 공모주 일정을 확인하는 모바일 사용자. 작업명: 공모아. 최종 브랜드 이름은 변경할 수 있어요.

## 먼저 해결해야 하는 출시 조건

현재 [앱인토스 서비스 오픈 정책 §3-5, §3-6](https://developers-apps-in-toss.toss.im/intro/guide.md)는 증권 등 금융상품 관련 서비스와 특정 종목 추천·투자 전략 안내에 제한을 두고 있어요. 다만 추가 조사에서 ‘공모주 미리보기’의 운영사 소개와 주식 관련 서비스의 소명 후 승인 경험을 찾았어요. **단순 일정 조회도 무조건 불가라고 단정할 수 없으며, 서비스 기능을 제시해 개별 확인할 사안**으로 판단을 수정해요. 자세한 확인 수준과 근거는 [추가 조사](ELIGIBILITY-RESEARCH.md)에 정리했어요.

아래 설계와 구현은 로컬 검토 가능한 결과물이에요. 앱인토스가 허용하는 기능 범위를 확인한 뒤 배포를 결정해야 해요. 범위가 허용되지 않으면 별도 웹 서비스로 검토할 수 있지만, TDS 사용 범위는 앱인토스 제공에 제한되므로 다른 채널에 공개하기 전 독립 UI로 교체해야 해요. [TDS 이용 범위](https://developers-apps-in-toss.toss.im/design/components.md)

## 1. Pingrow에서 확인한 실제 방식

제공한 링크는 단일 레포가 아닌 GitHub 조직이에요. 공개 FE/BE/AI 저장소를 확인했고, 공모주 기능은 Flutter FE에 있어요.

| 확인 위치 | 확인한 동작 | 이번 구현 |
| --- | --- | --- |
| [schedule_getter.dart](https://github.com/Pingrow/2025_SEASONTHON_TEAM_55_FE/blob/main/lib/service/schedule_getter.dart) | 공개 Google Calendar ICS를 HTTP로 읽고 VEVENT의 제목·시작·종료를 파싱 | 초기 구현에서 참고했으며, 현재 수집은 DART 증권신고서로 교체 |
| [ipo_page.dart](https://github.com/Pingrow/2025_SEASONTHON_TEAM_55_FE/blob/main/lib/pages/main/ipo_page.dart) | 월간 달력 → 날짜 선택 → 해당 날짜 일정 목록 | 동일 탐색 구조 + 홈·검색·관심 저장 |
| 같은 파일의 이벤트 배치 | 시작일/기간 순 정렬 후 겹치는 일정을 다른 차선에 배치 | 기간 연결과 겹침 처리, 숨긴 일정 수 표시 |
| 종료일 순회 | `DTEND` 당일까지 포함 | RFC 5545의 exclusive 종료일로 수정 |

원본은 별도의 공모주 가격·경쟁률 API를 사용하지 않아요. 공모두라는 별도 제품의 전체 기능은 이 저장소에서 확인하지 못했어요. 이 프로젝트는 **확인한 공모주 캘린더 기능을 같은 수집 방식으로 재구성한 것**이에요. 이름·그래픽·소스 복제는 하지 않았어요.

초기에는 `공모주린이 - 공모주 청약일정`을 사용했지만, 사용자 결정에 따라 현재는 수집을 제거했어요. 현재 DART 공시 검색·지분증권 주요정보·최종 신고서 원문을 조합해 청약기일을 읽어요. [현재 데이터 규칙](DART-DATA.md)을 참고해 주세요.

## 2. 성공한 미니앱에서 무엇을 가져왔나

아래의 성과는 공식 파트너 인터뷰에 게재된 특정 시점의 수치예요. 현재 실적이나 재현 가능한 성과를 뜻하지 않아요. 직접 토스 앱에 접속해 모든 화면을 실측한 분석이 아니라, **공개 인터뷰·공개 화면 자료·공식 UX 가이드에 근거한 분석**이에요. 서비스의 전체 전환율·리텐션 수치는 공개되지 않았어요.

| 사례와 공식 근거 | 공개 자료에서 확인한 흐름/성과 | 공모아에 적용한 설계 판단 |
| --- | --- | --- |
| [두쫀쿠맵, 2026-02-05](https://toss.im/apps-in-toss/blog/dubaicookiemap) | 재고 조회라는 한 가지 문제에 집중. 설치·초기 로그인 부담을 줄임. 관심 매장 재입고 알림으로 재방문 연결. 2월 1주 기준 MAU 108만을 소개 | 첫 진입은 로그인·권한 요청 없이 일정부터 표시. 관심 종목을 저장한 뒤 다시 찾아오게 함. 푸시는 별도 운영 구축 후 판단 |
| [디스팟, 2025-09-30](https://toss.im/apps-in-toss/blog/discountspot) | 할인코드 확인 → 제휴 브랜드에서 사용/구매. 첫 달 매출 약 1,000만 원을 소개. 사용자 데이터로 인기순 정렬 등을 개선 | 목록 → 정보 상세 → 저장이라는 짧은 행동 단위. 날짜순 정렬을 기본으로 사용자가 결과를 예측하게 함 |
| [매일 상식 쌓기, 2026-04-24](https://toss.im/apps-in-toss/blog/groundcode) | 5060 대상 매일 퀴즈와 리워드. 인터뷰 시점 일 수익 약 10만 원. 쉬운 문제와 TDS 활용을 강조 | 초보자 용어 설명, 큰 주 행동 버튼, 반복적으로 확인할 날짜 중심 홈. 단, 리워드와 금융 정보를 결합하는 모델은 적용하지 않음 |

공통점은 많은 기능보다 **즉시 얻는 효용 → 작은 완료 행동 → 다시 올 이유**가 명확하다는 점이라고 판단했어요. 공모아에서는 이를 `다가오는 청약 확인 → 관심 저장 → 일정 재확인`으로 번역했어요. 알림을 넣는 것만으로 리텐션이 올라간다고 가정하지 않아요.

## 3. 사용자의 질문과 화면 우선순위

| 화면 | 먼저 답할 질문 | 주 행동 | 화면에 배치한 정보 |
| --- | --- | --- | --- |
| 홈 | 지금 가장 가까운 청약은 언제인가요? | 청약 일정 자세히 보기 | 가까운 종목·기간·D-day·7일 날짜 띠, 다음 일정 |
| 전체 일정 | 특정 날짜에 무엇이 있나요? | 날짜 선택 또는 검색 | 월간 달력/목록, 종류 필터, 스팩 제외, 선택일 목록 |
| 상세 | 이 종목의 공시 청약기일과 출처는 무엇인가요? | 관심 저장/캘린더 내보내기 | 공시 청약기일·인수인·모집가액, 접수번호·접수일·납입기일·원문 링크 |
| 관심 일정 | 내가 보관한 일정은 무엇인가요? | 내보내기 또는 해제 | 예정/전체 분리, 기기 저장 설명, ICS 내보내기 |
| 안내 | 청약과 이 데이터는 어떻게 이해하나요? | 읽고 닫기 | 청약 순서, 출처, 저장 방식 설명 |

## 4. 주요 사용자 흐름

**처음 온 사용자:** 토스/브라우저 진입 → 홈의 가까운 청약 확인 → 상세 → 관심 저장 → 확인 메시지. 가입 화면이나 첫 진입 동의 시트가 끼어들지 않아요.

**날짜를 아는 사용자:** 전체 일정 → 월 이동 → 날짜 선택 → 해당 날짜 목록 → 상세. 기간이 있는 청약은 모든 포함 날짜에 표시하고 마지막 날 다음 날에는 표시하지 않아요.

**종목을 아는 사용자:** 전체 일정 → 이름/증권사 검색 → 달력과 목록에 같은 필터 적용 → 상세 → 원본 확인.

**재방문 사용자:** 관심 일정 → 예정된 일정 → 상세에서 변경 여부 재확인 → 필요 시 ICS 파일 내보내기. 종료된 저장 기록은 ‘전체’에서 볼 수 있어요.

**장애 시:** 처음부터 수집 실패 → 연결 안내와 다시 불러오기. 기존 정상 데이터가 있다면 유지 → 마지막 확인 시각·오래된 데이터 안내 → 다시 시도. 예시 데이터로 채우지 않아요.

**뒤로가기:** 상세/안내 닫기 → 원래 탭. 브라우저 이력 이동과 토스 네이티브 뒤로가기를 처리해요. 진입점은 `#home`, `#calendar`, `#saved`, `#calendar/event/{UID}`예요.

## 5. UI/UX 원칙

[공식 UI/UX 가이드](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide.md)에 맞춰 첫 화면을 막는 광고·알림 동의 시트 없이 시작하고, 클릭 결과를 예상할 수 있는 문구를 사용해요. 모바일 하단은 3개 목적지를 가진 플로팅 탭바로 구현했어요. 토스 기본 메인 탭바와 구분되는 모양이에요.

TDS 제공자와 실제 TDS 버튼을 사용해요. 독립 브랜드 ‘공모아’와 청록색을 사용하고, 날짜·기간에 강조를 집중해요. 상태는 색과 ‘내일/오늘 마감/종료’ 문구를 함께 보여줘요. 모바일은 한 열, 태블릿은 두 열, 데스크톱은 사이드바와 두 열을 사용해요. 날짜·검색·저장 컨트롤에는 접근 가능한 이름과 선택 상태가 있어요. 상세는 네이티브 HTML dialog로 초점을 가두고 Escape로 닫을 수 있어요.

| P0 | 상세·원본 출처·관심 저장·ICS 내보내기 | 구현·브라우저 테스트 완료 |

| P1 | 명시적으로 동의한 사용자에게 기능성 일정 알림, 발송 이력/해지 | 미구현. 로그인 식별과 서버 작업 필요 |
| P1 | 기기 간 관심 동기화, 변경 내역 | 미구현 |

자동 청약·매매·추천 종목·수익 예측·AI 투자 상담·가짜 경쟁률은 범위에서 제외했어요. OpenDART 청약기일에 원문으로 확인한 환불·상장 예정일과 증권사별 청약 조건을 추가했어요. iM증권·삼성증권·대신증권의 공개 경쟁률 집계를 지원하며 다른 증권사는 미지원으로 구분해요. ‘청약 비교’는 최대 3개 공모를 증권사별로 비교하고 직접 입력한 최종 경쟁률·청약 규모의 가정을 계산해요. 납입기일·배정공고일은 환불일과 구분해요. 회사 고유번호와 최초 제출일로 공모 회차를 구분하며 정정 후에도 저장 ID를 유지해요. 상세 규칙과 미지원 항목은 [경쟁률 데이터 문서](COMPETITION-DATA.md)에 정리했어요.

## 7. 검증할 지표와 수익 모델

첫 진입 상세 조회율, 상세에서 관심 저장률, 관심 사용자 D7 재방문율, 데이터 오류 신고율과 수집 실패율을 측정할 대상으로 제안해요. 아직 이용자가 없으므로 성공 수치나 목표 전환율을 임의로 제시하지 않았어요. 현재 앱은 개인정보·분석 이벤트를 외부로 전송하지 않아요.

노출/상세/저장/내보내기/재방문의 이벤트 정의와 개인정보 처리 범위를 먼저 정하고, 실제 출시가 허용된 뒤 계측을 붙여요. 초기 수익화는 미정이에요. 청약 정보 확인을 막는 광고, 저장과 보상 광고의 강제 결합, 증권사 추천 수수료를 전제로 하지 않아요. 2026년 10월 정책은 이전 성공 사례 시점과 다를 수 있어요.
