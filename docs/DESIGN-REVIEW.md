# 디자인과 검증 기록

## 디자인 방향

`design-taste-frontend` 앱 화면 워크플로를 적용했어요. 선택한 방향은 **Pastel consumer**, seed **2140653618**이에요. 앱인토스/TDS 맥락에 맞춰 팔레트와 서체를 유지하는 옵션을 사용했고 별도 재추첨은 없었어요.

선택 이유는 금융 정보의 짧은 확인 흐름에 부드러운 표면 구분이 적합해서예요. 브랜드는 공모아, 청록색 `#087f70`, Pretendard를 사용해요. 고유 요소는 **가장 가까운 청약의 실제 기간이 칠해지는 7일 날짜 띠**예요. 홈의 큰 종목명과 기간, 달력·상세·파일이 모두 같은 데이터에서 나와요. 수익률 차트나 임의 지표는 넣지 않았어요.

화면의 질문은 홈 ‘다음 청약은 언제인가’, 전체 일정 ‘이날 무슨 일정이 있는가’, 상세 ‘이 종목의 일정은 무엇인가’, 관심 ‘내가 보관한 일정은 무엇인가’예요.

## 화면 검토

1440px, 768px, 390px를 실제 Edge 렌더링으로 확인했어요. 초기에는 TDS 전역 스타일 때문에 흰 배경·링크색·서체가 제품 스타일과 충돌했는데 제품 루트에 명시적인 스타일을 적용해 수정했어요. TDS 버튼은 그대로 사용하고 모서리와 평면 피드백만 조정했어요.

최종 화면은 날짜·상태에 강조를 두고 일반 숫자는 검정/회색으로 정리했어요. 모바일에서는 전체 일정이 한 열로 바뀌고 선택일 목록이 아래로 이어져요. 가로 스크롤이 생기지 않는 것을 테스트해요. 하단 플로팅 탭은 스크롤로 모든 콘텐츠에 접근할 수 있도록 아래 여백을 확보했어요.

달력 숫자·범례·업데이트 시각 등 보조 요소가 11~12px인 점은 자동 검사에서 작은 글자 경고로 남을 수 있어요. 주 정보인 종목명·일정 기간·행동 버튼은 14~29px로 유지해요. 이는 밀도 높은 달력의 보조 표시에만 한정한 선택이에요.

홈과 달력의 자동 디자인 검사에서 FAIL은 없었어요. 달력의 ‘색상 데이터 없음’은 연한 청록 기간 막대를 차트의 데이터로 인식하지 못한 경고이며 실제 캡처에서 기간 색을 확인했어요. 빈 날짜 카드의 여백은 짧은 안내 문구의 상하 여백이에요. 소스 검사에 나온 그림자는 선택 날짜의 inset 테두리와 떠 있는 탭바/토스트에 한정해요. 상세 제목 위 라벨은 구분에 필요한 ‘청약/상장’ 데이터 상태예요.

실제 피드만 사용하고, 앱 화면에 교체할 가짜 고객·금액·종목 데이터는 없어요. 자동 테스트의 합성 종목은 `tests/browser/flows.spec.ts` 안에만 있어요.

## 검증 범위

- 날짜/ICS/캐시 단위 테스트: 한국·UTC·미국 시간대, 종료일 제외, UTC 자정 경계, 취소, 줄 접기, 주관사 오인 방지, 차선 재사용, 윤년/월말, 한국어 파일 왕복, 동시 수집·stale·초기 장애.
- Edge 모바일/데스크톱 사용자 흐름 테스트: 상세·저장·새로고침 후 유지·해제·ICS 다운로드, 달력·검색·필터·스팩 제외·월 이동, 직접 링크·Escape·브라우저 뒤로가기·안내, 장애·재시도·빈 피드·stale.
- TypeScript 검사, Vite 프로덕션 웹 빌드, Node 24의 앱인토스 `.ait` 패키징.
- 실제 피드 API를 이용한 화면 캡처와 3개 너비 디자인 검사.

네이티브 토스 파일 저장·네이티브 뒤로가기·Safe Area는 SDK 타입에 맞춰 연동했지만, 실제 토스 iOS/Android 검증 완료를 의미하지 않아요. 앱인토스 심사·출시도 수행하지 않았어요.

2026-10-25 DART 전환 후 실행 결과: 단위 테스트 17/17, Edge 모바일·데스크톱 사용자 흐름 8/8, TypeScript·웹 빌드·`.ait` 패키징 성공. 날짜 해석, 정정 전후 식별자 유지, 공모 여부·원문 접수번호 검증, 최신 원문 표 추출, 페이지 수집, 동시 수집·stale·키 오류를 확인했어요. 실제 DART 데이터로 청약 일정 28개(다가오는 일정 21개)를 수집했고 확인이 어려운 공시 3개는 제외했어요. 이 수치는 검증 시점의 수집 범위이며 전체 공모주를 빠짐없이 포함한다는 의미는 아니에요.

실제 DART 데이터를 사용한 3개 너비 × 3개 화면에서 브라우저 런타임 오류 0건을 확인했어요. [홈](screenshots/desktop-home.png), [모바일 달력](screenshots/mobile-calendar.png), [모바일 상세](screenshots/mobile-detail.png)를 확인할 수 있어요. 인증키가 공개 웹 산출물과 데이터 캐시에 포함되지 않는 것도 확인했어요. 기존 관심 목록은 이전 출처로 구분해 보존하며, DART에 없는 환불일·상장일은 추정하지 않아요.

같은 날 주관사 누락 보완 후 단위 테스트 20/20, 모바일·데스크톱 사용자 흐름 12/12, TypeScript·웹 빌드·`.ait` 패키징을 통과했어요. 실제 원문에서 `대표`로 표기된 SK증권·한화투자증권·아이엠증권을 읽도록 보완해 수집 일정 28개의 주관사·모집가액 미확인이 각각 0건이 됐어요. 누락 시 화면 안내와 원문 링크, 원문 보완 시 확인 근거와 증권사 검색 동작을 자동 검증했어요. 앞으로 모든 공시 서식을 지원한다는 의미는 아니며 매 수집마다 품질 집계를 남겨요.

## 청약 비교·환불·상장 예정일 확장

기존 Pastel consumer, seed 2140653618, Pretendard·청록색·날짜 띠를 유지했고 재추첨은 없어요. ‘청약 비교’의 질문은 **증권사별 집계와 청약 조건, 필요한 자금은 얼마인가**예요. 종목을 최대 3개 고르고 증권사별 열로 비교해요. 가정 계산은 화면 위의 버튼으로 바로 이동할 수 있어요.

첫 검토에서 종목 선택 보조 날짜가 10px로 작고, 모바일에서 첫 증권사의 숫자가 오른쪽으로 밀리는 문제가 있었어요. 보조 글자를 12px로 키우고 모바일 고정 항목 열 128px + 증권사 열 190px로 바꿨어요. 390px 화면의 콘텐츠 350px 안에 첫 열 318px가 들어가고 나머지 열은 표 프레임 안에서 가로로 넘겨 볼 수 있어요. 페이지 자체는 가로로 넘치지 않아요. 미확인 값의 색과 크기도 일반 보조 표기로 바꿨어요.

마지막 프로덕션 화면 검사에서 1440·768·390px 모두 FAIL 0건이에요. 보조 글자 13px 미만 비율 경고는 공시 원문 조건·출처·확인 시각·선택 종목의 날짜에 12px를 사용하기 때문이에요. 주요 데이터는 14px, 균등 참고수량이 있으면 22px로 표시해요. 실제 데이터 비교·가정 계산 화면과 홈·달력·상세의 3개 너비 캡처에서 런타임 오류와 페이지 가로 넘침이 없었어요.

검토 결과: 첫 화면은 종목·증권사·집계 상태와 주요 지표를 먼저 보여줘요. 긴 비교 표는 본문의 같은 좌우 경계를 사용하며 공시 조건 발췌 때문에 길어지는 행은 그대로 읽을 수 있어요. 색은 실제 균등 참고값과 날짜 상태에만 사용해요. 수치·총 증거금·최소 증거금은 원본 필드에서 계산하며 가정 계산은 별도 입력을 사용해요. ‘청약 전’, 실제 0, 미확인, 연동 미지원, 과거 집계를 구분해요. 범례는 실제 있는 일정 종류만 표시하고 모바일에서 메뉴는 4개 하단 탭으로 접혀요. 주요 한계는 원문 조건 발췌의 정보 밀도와 아직 지원하지 않는 증권사예요.

검증은 단위 테스트 32개, 모바일·데스크톱 사용자 흐름 16개예요. 회사·청약기간 매칭, 일반청약과 기관/ELS 구분, 대신 월별 페이지 끝까지 조회, 원본 시각과 앱 수집 시각, 5분 캐시·stale, 같은 최초 제출일의 전문 보완, 날짜 출처 보존과 ICS URL, 계산 단위·한도·0분모를 확인했어요. 날짜 근거가 이미 있는 DART 메타데이터를 증권사 안내로 덮어쓰는 경우도 회귀 검증했어요. API 키가 공개 웹 산출물·캐시·패키지에 들어가지 않는 검사도 실행했어요.

최종 화면: [모바일 청약 비교](screenshots/mobile-comparison.png), [데스크톱 비교](screenshots/desktop-comparison.png), [모바일 가정 계산](screenshots/mobile-scenario.png). 캡처의 종목과 숫자는 실제 수집 데이터이며, 가정 계산 캡처에 입력한 경쟁률 100:1은 계산 동작 검토용 가정이에요.


## 2026-10-25 출시 범위 정리

- 등록명 공모두(gongmodu)로 화면·번들·내보내기 파일명을 맞췄어요. 기존 관심 저장 키는 보존했어요.
- 경쟁률 메뉴·상세 위젯·API 폴링·서버 경쟁률 경로를 제거했어요. 관련 연구 코드는 보류 상태로 보관해요.
- 단위 테스트 32개, 모바일/데스크톱 브라우저 사용자 흐름 16개가 통과했어요. 보류 경로 직접 진입과 API 미호출도 확인했어요.
- home/calendar/detail 스크린샷을 세 화면 크기에서 새로 촬영했고 런타임 오류가 없었어요. comparison/scenario 이미지는 이전 연구 기록이에요.


## 토스 실기기 피드백 반영

- 사용자가 토스에서 초기 버전 실행을 확인했고 홈의 달력 위치·제목·내보내기·누락 안내 배너 수정을 요청했어요.
- 기존 pastel-consumer 방향(seed 2140653618), 초록 브랜드와 Pretendard를 유지했어요. 새로운 스타일을 다시 추첨하지 않고 실제 일정이 우선 보이도록 순서를 바꿨어요.
- 홈의 질문은 “이번 달 공모주 일정은 언제인가요?”이며, 월간 달력을 DOM 첫 영역에 두고 날짜별 목록을 바로 연결했어요. 제목은 한 줄, 모바일 22px이에요.
- 내보내기·토스 파일 저장·내보내기 안내를 제거했고, 기존 관심 저장 키는 보존했어요. 공시 해석 누락 배너를 제거했으며 원문 링크·오류·stale 표시는 유지해요.
- 프로덕션 빌드의 1440/768/390px 검사에서 FAIL 0개. 11~12px 달력 날짜/종목 라벨 때문에 작은 글씨 비중 경고가 있어요. 달력은 최소 11px을 유지하고 상세에서 전체 종목명을 확인해요. 두 번째 경고는 달력과 우측의 쌓인 패널을 개별 카드로 비교한 높이 차이이며 실제 두 열 전체의 하단은 비슷해요.
- 35개 데이터 단위 테스트, 18개 모바일/데스크톱 사용자 흐름을 검증해요. 달력의 첫 화면 노출, 날짜 선택, 내보내기 미노출도 포함해요.
